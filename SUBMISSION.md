- **Otari features used:**
  - OpenAI-compatible gateway — one workspace API key in front of a 174-model catalog; only the `base_url` changes (`https://api.otari.ai/api/v1`).
  - Three open-weight models in distinct roles through that one key: planner `openai/gpt-oss-20b`, researcher `deepseek/deepseek-v4.1-flash-1017`, critic `z-ai/glm-5.3-flash`. Main pipeline: 3 calls, 2,413 tokens, ≈ $0.0005, VERDICT: PASS.
  - Per-API-key budgets enforced before dispatch: main key capped at $0.50 ($0.02 spent per the dashboard); a second key capped at $0.001, already ≈ $0.0043 spent, was refused on call 1 (HTTP 403, `budget_exceeded`, 0 successful calls).
  - `otari_code_execution` — fired server-side; computed a monthly spend of exactly $3.00 and a $2 cap binding at 333 calls/day (VERDICT: PASS). The assistant message carries no `tool_calls` array, but the raw response's `otari_tool_calls` array reports each execution's status.
  - `otari_web_search` — executed in standalone isolated calls (5 sources returned, $0.010383, completion id `chatcmpl-RQxeMe4VSOFWljhEjjPOZKOc`) and, in the project's final run, inside a dedicated retrieval stage: 3/3 planner queries searched, 20 unique sources collected, cited synthesis, critic VERDICT: PASS (final run: 9 calls, 23,284 tokens, $0.042818 at the gateway's own reported prices). Inside the multi-call agent sequence its executions were refused with `budget_exceeded` tool errors, and on a key carrying a per-key budget they are refused anywhere — so the retrieval stage runs its searches on the workspace's spare key (no per-key budget) and logs that it did. All stated honestly, and filed as an issue.
  - Workspace "Allow web access" toggle — enabling it flipped all three gateway tools to available in `GET /api/v1/tools`. Tools run totals: 4 calls, 14,384 tokens, ≈ $0.002 of model calls.
  - Tools preflight — before any tools-declaring call, the client queries `GET /api/v1/tools` and declares only what the workspace reports available (declaring a disabled tool gets the whole call refused with a bare 403). Per-request cost readback — every response's raw usage object carries `cost_usd`, and the client prints it per call.
  - Not used: routing policies (none configured) and guardrail profiles — checked properly: `GET /api/v1/tool-settings/guardrails/profiles` answers `{"available": false, "reason": "No guardrails service is configured…"}` on the hosted deployment, and a per-request profile reports `unavailable / not_configured` in the `Otari-Guardrails` header without evaluating anything. Nothing claims them.

- **Feedback:** Full written feedback is in FEEDBACK.md (kept alongside this file and copied into the repo). Summary: what worked is the core promise — OpenAI-compatible access to 174 models behind one key, and per-key budgets enforced before dispatch (a $0.001-capped key refused on call 1). What didn't work is observability: `GET /api/v1/key` 404s though documented, `/usage` is master-key-only, completion ids don't resolve in `/usage/requests/{id}`, and tool executions inside an agent sequence hit an undocumented `budget_exceeded` while standalone calls succeed (declaring `otari_web_fetch` in the sequence also 422'd the whole request). Most-tempted-to-skip moment: debugging blind on spend readback and tool refusals. Would I keep using Otari without the rules? Yes — for the budgets and the one-key multi-model routing. The enforcement is ahead of the observability.
